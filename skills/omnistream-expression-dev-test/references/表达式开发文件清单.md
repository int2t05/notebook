# OmniStream 表达式开发文件清单

> 配套文档:[表达式开发指南.md](表达式开发指南.md)(权威总纲)、`omnioperator-expression-dev` skill、`omniadaptor-vectorized-expression` skill。
>
> 本篇聚焦一个问题:**开发一个表达式,到底要动哪些文件?每个文件为什么必须写?** 按仓库 × 类型组织,新手可据此建立"文件地图"。
>
> 适用版本:OmniOperator 2.1.0 / OmniStream 1.2.0 / OmniAdaptor 2.1.0

---

## 0. 这篇文档解决什么问题

开发一个 Flink SQL 表达式(如 `REVERSE`、`IFNULL`、`STDDEV_POP`、`json_value`)使其走 native 加速,代码改动会散落在 **2~4 个文件**、**2~3 个仓库**里。新手常见的困惑:

- 不知道该改 Java 还是 C++?
- 不知道 OmniOperator 侧该用向量化路径还是 row JIT 路径?
- 改完一个文件,不知道还有哪些配套文件必须同步改?
- 为什么我改了实现,运行期还是报 `Function not supported`?

本文给你一张"文件地图":先讲全局数据流(理解每个文件**为什么存在**),再按类型给清单(知道**该改哪些**)。

## 1. 先建立全局观:三仓库 + 数据流

### 1.1 三仓库职责

| 仓库 | 语言 | 职责 | 在表达式开发中的角色 |
| --- | --- | --- | --- |
| **OmniAdaptor** | Java | Flink/Calcite 桥接:算子替换决策、把 RexCall 翻译成 JSON 表达式协议 | 表达式的**入口**:决定表达式长什么样、能否进 native |
| **OmniStream** | C++ | Native 运行时框架:Task/OperatorChain/算子调度 | **基本不动**:向量化计算全权委托 OmniOperator |
| **OmniOperator** | C++ | 向量化内核:Expr 树、JSONParser、LLVM JIT codegen、150+ 函数库 | 表达式的**实现**:JSON→Expr→机器码→执行 |

> 一句话:**OmniAdaptor 负责把表达式"翻译"出来,OmniOperator 负责"执行"它,OmniStream 只当搬运工。**

### 1.2 一条表达式从 SQL 到 native 的数据流(5 阶段)

```
用户 SQL (Flink SQL)
  ↓  Calcite 解析 & 优化
┌─────────────────────────────────────────────────┐
│ 阶段1 规划期 (Java, Client)                       │
│   OmniAdaptor / RexNodeUtil.java                 │ ← 识别表达式,翻译成 JSON AST
│   ValidateCalcOPStrategy 白名单校验               │ ← 挡掉非法/不支持的表达式
├─────────────────────────────────────────────────┤
│ 阶段2 部署期 (Java, Client)                       │
│   JSON AST 嵌入算子链 → 序列化到 JobGraph         │
├─────────────────────────────────────────────────┤
│ 阶段3 解析期 (C++, TaskManager)                   │
│   OmniStream / StreamCalcBatch                   │ ← 收 JSON,转发给 OmniOperator
│   JSONParser::ParseJSON() → Expr 树              │ ← JSON 反序列化成内存表达式树
├─────────────────────────────────────────────────┤
│ 阶段4 编译期 (C++, OmniOperator)                  │
│   ExprVerifier 验证语义                           │ ← 判定能否向量化/codegen
│   ExpressionEvaluator → LLVM CodeGen             │ ← Expr 树 → LLVM IR → 机器码
├─────────────────────────────────────────────────┤
│ 阶段5 运行期 (C++, OmniOperator + OmniStream)     │
│   FilterFunc / ProjFunc 批量向量化执行            │ ← 在 VectorBatch 上跑机器码
└─────────────────────────────────────────────────┘
```

**关键认知**:上面每个阶段都对应不同文件。所谓"开发一个表达式",本质就是在这些阶段的"插桩点"上加上对新函数的支持:

- 阶段1 要让 adaptor 认识它 → 改 `RexNodeUtil.java` + 字典
- 阶段3 要让 parser 能解析它 → 改 `jsonparser.cpp`(仅特殊语法)
- 阶段4 要有它的实现 → 改 OmniOperator 函数实现 + 注册
- 阶段5 自动跑,不用动

### 1.3 一个核心区分:两类文件

| 类别 | 什么时候写 | 例子 |
| --- | --- | --- |
| **每表达式都要写的"交付物文件"** | 每开发一个新函数都要新增/修改 | 函数实现 `.h/.cpp`、注册 `Register*.cpp`、单测、`RexNodeUtil.java` |
| **框架文件(运行时骨架)** | 不是每个表达式都动,只在特殊语法/新类型时才扩展 | `expressions.h`、`jsonparser.cpp`、`ExprEval.cpp`、`codegen` |

新手容易把"框架文件"当成每个函数都要改的地方——其实大多数标量函数(Type A)只动"交付物文件",框架文件已经就绪。

## 2. 四种表达式类型(决定改哪些文件)

这是最重要的分类,直接决定你改哪些文件:

| 类型 | 触发词 | JSON exprType | 改动范围 | 典型示例 |
| --- | --- | --- | --- | --- |
| **Type A** | 标量函数 | `FUNCTION` | OmniAdaptor + OmniOperator | `REVERSE`、`MD5`、`char_length` |
| **Type B** | 特殊语法 | 自定义 exprType | OmniAdaptor + OmniOperator(jsonparser) | `BETWEEN`、`NULLIF` |
| **Type C** | 聚合函数 | 算子级 `aggInfoList` | OmniAdaptor + OmniStream + OmniOperator | `STDDEV_POP`、`PERCENTILE` |
| **Type D** | SQL 变体(别名) | `FUNCTION` | **仅 OmniAdaptor** | `UPPER`→`upper`、`IFNULL`→`COALESCE` |

### 2.1 Type A 的两条子路径(关键决策)

Type A 标量函数在 OmniOperator 侧有**两条注册路径**。JSON 侧(`RexNodeUtil`)完全一样(都发 `FUNCTION` + `function_name`),区别只在 OmniOperator 注册到哪张表、函数写在哪:

| 子路径 | 适用场景 | 实现位置 | 注册位置 | 标杆示例 |
| --- | --- | --- | --- | --- |
| **向量化** | 纯列式可向量化、追求吞吐 | `core/src/vectorization/functions/<Name>.{h,cpp}` | `core/src/vectorization/registration/Register*.cpp` | `char_length`、`left/right` |
| **row JIT** | 逐行复杂逻辑/需外部上下文(JSON 缓存、正则) | `core/src/codegen/functions/<domain>functions.{h,cpp}` | `core/src/codegen/func_registry_<domain>.cpp` | `json_value`、`REVERSE` |

> **怎么选?** 纯数值/字符串运算、能整列批量处理的 → 向量化路径(默认首选,吞吐高)。需要逐行复杂逻辑、需要 `ExecutionContext`(如 JSON 缓存)的 → row JIT 路径。两条路径的 C 函数规范不同(向量化用 `call()`/`callNullable()` 返回 `Status`/`bool`/`void`;row JIT 用 `extern "C"` 三元组参数),开发前先判定。

**`call()` 返回值三约定**(向量化路径核心,决定 NULL 处理):

| 返回类型 | 含义 | 适用 |
| --- | --- | --- |
| `Status` | `Status::OK()` 成功 / `Status::UserError(...)` 出错;null 由向量框架处理 | 算术/math/bitwise |
| `bool` | `true`=有效结果,`false`=输出 NULL(bool 成为输出向量的 null 标志) | 字符串/比较 |
| `void` | 总是非 NULL 结果(`notNull=true`) | 必然非空 |

#### Type B — 特殊语法(新 exprType)

> 这类表达式**不是普通函数调用**,有特殊语法(如 `BETWEEN`、`NULLIF`),需要在 JSONParser 里加新分支。

| # | 文件 | 为什么写 | 是否必须 |
| --- | --- | --- | --- |
| 15 | `core/src/expression/jsonparser/jsonparser.cpp`+`jsonparser.h` | `ParseJSON()` if-else 链加新 exprType 分支 + `ParseJSONXxx()` 方法,把新 JSON 结构解析成 Expr 树 | Type B 必须 |
| 16 | `core/src/expression/expressions.h`+`expressions.cpp` | 仅当需**全新 Expr AST 类**时(如 `BetweenExpr`)。⚠️ 加成员/新 virtual 槽 = ABI 破坏,需 `omnistream_incr` 重编 OmniStream | 需新 Expr 类时 |
| 17 | `core/src/codegen/expression_codegen.cpp`+`batch_expression_codegen.cpp` | 为新 Expr 类加 `Visit(const XxxExpr&)` 的 LLVM codegen(行级 + 批向量化)。如 `BetweenExpr` 的 codegen 把 `x BETWEEN a AND b` lower 成 `batch_lessThanEqual`×2 + `batch_and` | 需新 Expr 类时 |

> **BETWEEN 实例**(已落地,Type B-①):adaptor 不改写成 `>= AND <=`,而是产出专用 `exprType:"BETWEEN"`(value/lower_bound/upper_bound)→ `BetweenExpr`(`expressions.h:333`)→ 解释器 `ExprEval::Visit(const BetweenExpr&)` 是**空 stub**,靠 codegen(`batch_expression_codegen.cpp:1741`)lower 到已有向量化原语 `batch_lessThanEqual`×2 + `batch_and`。即:有专用 AST + 专用 codegen,但**无专用向量化解释器函数**。
>
> **SIMILAR TO 实例**(Type B-②):语义拆不开(正则)→ **造专用 `SimilarFunction`**(`functions/Similar.h`,re2)+ 注册 `similar_to`(`RegisterRegexp.cpp:17`),ExprEval `Visit` 调 `Apply`(**活**),codegen `Visit` 返回 invalid(stub)走解释器。即:有专用 AST + 专用函数,但 codegen 不实现。**Type B 两支判据**:语义能拆成已有原语→B-①(BETWEEN,借原语走 codegen);拆不开→B-②(SIMILAR TO,造函数走解释器)。详见 [`表达式开发路径选择-向量化函数vs-codegen.md`](表达式开发路径选择-向量化函数vs-codegen.md)。

#### Type C — 聚合函数

| # | 文件 | 为什么写 | 是否必须 |
| --- | --- | --- | --- |
| 18 | `core/src/operator/aggregation/`(+`aggregator_factory.cpp`) | **聚合算子实现**:`Aggregator` 子类(`Init`/`Update`/`Merge`/`GetResult`)+ 工厂注册映射。不走 JSONParser→CodeGen,在 HashAgg Operator 内执行 | Type C 必须 |

### 3.3 OmniStream(C++ 运行时)

**基本不写文件**。`cpp/streaming/api/operators/StreamCalcBatch.h` 纯转发 OmniOperator(直接 include `jsonparser.h`/`expr_evaluator.h`,CLAUDE.md 明确"不在 OmniStream 重写 codegen/expression")。

**只有以下 ABI 破坏性改动才需改 OmniStream 并 `omnistream_incr` 重编**:
- Type B 新增 Expr 类(头文件加成员/新 virtual 槽)
- Type C 算子级改动

仅 `.cpp`-only 的 OmniOperator 改动(如 Type A 加函数)→ 只重编 `.so` + `deploy`,**不必重编 OmniStream**。

## 6. 两个必踩的坑(贯穿所有类型)

### 坑 1:注册名 ≠ function_name(大小写敏感)→ 运行期 `Function not supported`

`Register*.cpp` / `func_registry_*.cpp` 里的注册名,必须与 `RexNodeUtil` 生成的 `function_name` **完全一致(大小写敏感)**。不一致则 adaptor 翻译的 JSON 在 native 运行期 `jsonparser.cpp` 查不到函数,报 `Function not supported`。

> **反例 `char_length`**:`RegisterString.cpp` 注册名写成 `"length"` ≠ SQL `char_length`,导致虽然有 `CharLengthFunction` 实现,native 仍 not supported。

### 坑 2:改 RexNodeUtil 前不调研 → 类型不支持 / 语义不一致

动 `RexNodeUtil.java` 前,必须先核对(`omniadaptor-vectorized-expression` skill 步骤 1):

1. **Flink 侧语义/类型**:`omnihelper/resources/flink_function_dictionary.json` 里该函数允许哪些入参类型、NULL 行为、边界行为。
2. **OmniOperator 向量化注册类型**:`Register*.cpp` 里该函数注册了哪些入参 OMNI 类型重载、`call()` 语义是否与 Flink 一致。
3. **入参类型匹配**:把"RexNodeUtil 将传入的类型"与"向量化已注册的类型"逐一比对。

跳过调研会导致:类型不支持(未注册)、语义不一致(下标基准/NULL/边界/时区差异)、或需要新增 OmniOperator 实现却不自知。

## 7. 完整示例:走 Type A 向量化实现一个函数

以实现 `ABS`(取绝对值)为例,完整改动顺序:

**步骤 1 — 调研**(动代码前):查字典确认 ABS 支持 `BIGINT/INTEGER/DOUBLE`;查 `Register*.cpp` 确认 `abs` 注册了对应类型重载;确认 `call()` 语义(返回绝对值,null 由框架处理)与 Flink 一致。

**步骤 2 — OmniAdaptor 适配**(2 文件 4 处):

`flink_function_dictionary.json`:
```json
{"func_name": "ABS", "is_support_func": true, "is_supported_type": ["BIGINT", "INTEGER", "DOUBLE"]}
```

`RexNodeUtil.java` 3 处(见 §3.1 模板):`specialOperatorMap` + `SpecialExprType.ABS` + `buildJsonMap` case(生成 `function_name:"abs"`)。

**步骤 3 — OmniOperator 实现**(向量化路径,3 文件):

`core/src/vectorization/functions/Abs.h` — 函数类(`call()` 返回 `Status`,null 由框架处理)。
`core/src/vectorization/registration/RegisterMath.cpp` — `RegisterFunction<AbsFunction, ...>(prefix+"abs", {OMNI_INT/OMNI_LONG/OMNI_DOUBLE}, ...)` 三个类型重载。
